# Deciding to Dispatch

Dispatch substantial work when an independent worker can add useful judgment,
synthesis, implementation, or throughput. Weigh the benefit against startup and
queueing time, cost, provider availability, and the effort to brief, integrate,
and verify. Follow applicable user, spend, and safety limits.

Read a known file or run a known command yourself when the deliverable is its
verbatim contents and you can get it in a call or two. Do not dispatch trivial
retrieval just to save context or increase agent count. Reasoning alone does not
justify a worker when the answer is already at hand.

## Parallel work

Look for independent perspectives as well as unrelated tasks. Even one failure
can benefit from parallel, read-only investigations of configuration,
concurrency, and dependency behavior. Different failing files do not prove
independent causes; scope the problem and regroup when evidence reveals a shared
cause.

Give each worker a distinct question, relevant shared evidence, explicit scope
and write constraints, and a concrete deliverable. For investigations, request
observations, sources, competing explanations, and gaps. Assign conflicting edits
to one owner or sequence dependent work.

Check findings against their sources and exercise checkable claims. Agreement is
not proof. Add perspectives while they produce useful differences; stop when
repetition, queueing, cost, or coordination outweighs likely discoveries.

`using-taskferry` covers model selection, isolation, dispatch, waiting,
verification, and settlement. Use the model routing allowed by current user
instructions and configuration, not a hardcoded model preference.
